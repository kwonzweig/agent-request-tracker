# Request Tracker

Use only for a conversation explicitly enrolled in Request Tracker. Other conversations remain unaffected.

Keep the human's original outcome and explicit permissions separate from your proposals and assumptions.

Humanizer is mandatory for every human-facing response and card in enrolled conversations. Load the available `humanizer` skill before the first response and apply its embedded rewrite process before every later response, including progress updates. Reuse the loaded instructions; do not reread or announce them on every turn. Preserve facts, required context, fixed product labels, and technical terms. Remove filler, duplicated status, unexplained internal references, and metadata strings. If Humanizer is unavailable, report the missing dependency once; never claim it was applied. This requirement belongs in the response entrypoint, not an optional writing task.

Call `journal_read` with the actual conversation id at intake. Treat a new correction or status question as steering the standing request unless the user cancels or replaces it. After answering, continue the authorized work. Do not call a document update a completed product.

`journal_read` and `journal_update` are silent persistence tools. Save intermediate changes without mounting another card. Call `journal_show` once when the human should read the final journal. An already open widget may refresh saved state; do not promise to hide older host messages or call show for every checkpoint. A failed display does not erase a successful save.

Bind `turn.id` to the actual current host turn, supplied by a hook or a supported conversation reader. In Codex desktop, when available, read this conversation's newest turn through `read_thread` and use its returned id. Reuse that id throughout the turn; a test-case number is not a host turn id. If the host exposes no turn identity, use an explicitly `manual-` checkpoint and note the unavailable binding in its source. Never fabricate a native identifier or read unrelated conversations to obtain one.

Maintain Request, Decision, and Blocker records across human turns. One Request represents one requested outcome, not one message or turn: update the same record through clarifications, progress and completion. Use `cards` for Suggestion, Q&A, and Note without turning ordinary questions and information into new tasks. A Request needs its source, outcome, done conditions, parent, and state. A Decision needs its question revision, options, recommendation, no-answer behavior, and actual user answer separate from any assumption. A Blocker needs affected work, evidence, next action, and owner. A Suggestion is optional and never itself justifies stopping. Keep conversation-local private records out of source control.

Saving a Request as `done` automatically creates one Complete card (`type: completion`) from its title, evidence and result links. Do not create a duplicate. A newly created Done Request also gets a card; old Done records are not backfilled. Repeated saves and evidence/link edits do not create new notices. The Request stays Done while its unread notification remains in Attention. Reopening retires the pending notice; a later completion or changed requested outcome gets a fresh one. Preserve the generated completion identity and content; reconcile acknowledgment through the same actual-user `resolution` or Comment rules as Note. An unread completion notification is not a blocker or a reason to stop independent work.

When an existing work item is relevant, set Request `workspace: {id, url}`: its human-readable ticket/PR label and verified HTTP(S) URL. Use the workspace established for this conversation; ask when the destination is genuinely ambiguous. Never fabricate a task, create a second tracker, or assume a company-specific service for unrelated work. Omit the field when no destination exists; use `null` to remove it. A link is navigation, not task synchronization or permission. Requests and Cards show current records; History derives each turn's changes and replies from saved events, so do not write duplicate records merely to populate a tab.

Before a human-facing final response:

1. Answer the actual question first. Reconcile changed requests, unresolved decisions, and blockers with the conversation-local journal.
2. Show only cards the human needs: Decision (why now, recommendation, consequences, no-answer behavior), Blocker (affected work, cause, exact next action and owner), or Note (important impact without a choice).
3. Submit concise changes to the persistent journal, then call `journal_show` once. Preserve unresolved items and source references for scope changes, cancellation and conditional approval. Textual deltas may supplement it but do not replace persistent tracking. Never print the entire JSON ledger by default.
4. Check the tool's saved revision without narrating it to the user. Saving and successful display are different; report a failure only when it affects the result. Completion needs evidence; a filled form does not prove completion.
5. Continue authorized work if no real boundary requires stopping. Do not invent 'continue?' decisions. Identify a real continuing run before claiming background progress.

Write for the person reading the response: name the affected request or product; explain what changed for them; say whether they need to act. Do not refer to 'the draft', 'the connection', 'the update' or 'the owner' without an identifiable subject. Name the actual execution path when delegation matters (ChatGPT session, native runner, or Codex subagent, with a link/model when verified). Keep internal file and protocol details out of the main explanation unless needed for the user's decision.

For a legitimate final response, make the reason evident: requested result delivered, a specific decision is required, a named obstacle needs an exact action, the user paused, or an identified worker is continuing. A progress checkpoint goes in commentary. 'The feature is still unimplemented' is not a reason to stop implementing it.

The renderer owns the Goal, execution status, badges and saved-state indicators. It omits the `Agent:` prefix. Do not repeat these in response prose. A request for “the result only” receives only that result; the persistent card supplies tracking separately. Record execution honestly: `Working` requires running-agent evidence, `Needs your input` an actionable required response, and `Paused` a user pause. Preserve unknown state when observation is unavailable. Never infer waiting merely because a response ended.

Use neutral option labels. Put the recommended option id only in `recommendation`; the renderer supplies the single `Recommended` badge. Do not add “(추천)”, “(Recommended)” or a second recommendation sentence to an option label.

Use the host's native question controls when supported and appropriate. The displayed question must match the journal decision revision. Silence, preselection, recommendation, and a user-submitted answer are different states.

Cards with answer choices offer `Other`; reveal its text field on selection and require nonblank text to submit that answer. Comment is a separate optional field, revealed by its icon, including beside choices and Other. Keep a choice and its accompanying comment as separate items in the same reply. Send selected answers and comments together, preserving the card id and revision internally. A comment is not automatically approval, a Blocker resolution, or a new task. Interpret it in context and retain it in History.

Users act, choose and comment; the agent interprets their meaning and maintains the records. Do not ask users to classify their comments, clean up obsolete cards or repeat a clear answer through a button. A missed card, silence, fatigue or a topic change never implies agreement or cancellation. Keep unanswered relevant cards in Attention, including Q&A, Note and Complete.

Blocker users can perform the requested step, report what happened through chat or Comment, choose **Later**, or select an **Alternative** with **Other** for another response. They have no Resolve action. Decision and Suggestion have choices, Other and Later. Q&A, Note and Complete have a top-right **×** (Mark as read) and Comment. Clicking × silently saves that card as read through the app-only writer. It never sends a chat message, creates a conversation turn, or starts the agent. Other choices and comments remain unsent. A failed save keeps the card visible; never fall back to a prompt. On the next actual user turn, reload the saved state without asking them to repeat the acknowledgment. Resolved is the saved status, never the button label. Unread Complete cards have no Open badge; the underlying Request is already Done. Do not expose lifecycle status pickers or a Blocker Dismiss action. Send reply submits choices and comments. Unsent drafts are not card states.

Attention cards remain expanded and omit the redundant Open badge. Cards keeps folding and shows × only on expanded, unread informational cards; History is read-only. Expanded cards put request and resource links beside Comment below the body. Collapsed entries keep their links below the title. An empty Attention says **No action needed.** It does not establish acknowledgment or work completion.

**Later** hides the card from Attention while retaining its constraint and history. Before dependent work resumes, check that constraint; a concrete dependency may justify reopening with a sourced reason and a short nudge. Elapsed time alone does not. Valid resolved or dismissed cards leave Attention without a second acknowledgment and remain in Cards and History. Empty Attention does not prove the requested work is complete.

A clear ordinary chat message or comment can answer, acknowledge, postpone or supersede a card. Interpret the full instruction, its target, version and limits. "Use A in the plan, but do not build" settles a design choice without permitting implementation. Clarify only when ambiguity affects a consequential choice. Never treat every comment as approval or refuse to interpret comments at all.

When revisiting Attention, check whether a saved reply or later user message already settled each item. Apply an attributable acknowledgment to the unchanged explanation instead of asking the user to repeat it. A preserved unsent draft cannot reopen a settled card or count as a new user answer.

An explicit human answer remains User-authored even when the agent saves it. Agent inference and optional working assumptions remain separately attributed to Agent with their source and reason; never fabricate `user_answer`. Required decisions cannot be answered by agent inference. When a card no longer applies, record Dismissed with a reason and source (and replacement when relevant), not a false resolution. Do not dismiss an unanswered necessary choice just to finish, cancel the user's outcome, or bypass an agreed path. A late reply must not reactivate an obsolete choice automatically.

Only the agent resolves a Blocker, after verifying the affected operation. "I signed in" reports an action; a successful access check establishes the result. Cite that verification in Agent `resolution` and bind `resolution.record_revision` to the blocker version you checked (its latest journal record-change revision). If the condition changed during verification, recheck it. If the check fails, keep the same blocker open with the observed failure and next action. An Alternative authorizes only that option; if it makes the original blocked step unnecessary, record a sourced Dismissed outcome rather than claiming a fix. Otherwise retain the obstacle. Older Blocker Resolve receipts remain historical reports, never verification or a reason to offer that action again. Q&A, Note and Complete resolution requires attributable acknowledgment, which may be a clear comment. Becoming irrelevant instead supports Dismissed, not a claim that the user understood.

Keep useful Background, Impact and Next action in named fields without duplicating the main explanation. Cards have no nested Details, Responsible, Source or Record display. Preserve provenance and IDs in the data. Use Request `workspace` for the primary work item and optional `urls: [{label,url}]` for other useful destinations. Cards inherit the linked Request's nearest workspace; explicit null stops inheritance. Links do not grant authority.

For a Request Tracker reply, read the accompanying JSON resource and the actual received human message together. Check its conversation and delivery ID, and each item's original record revision against journal history. Set optional `input_method: card` only for an actual card reply, or `chat` for an ordinary message recorded in context; omit it when unknown. The MCP writer stamps `recorded_at` when it stores a new receipt, not when the user acted. Do not invent or backfill old timestamps. Commit the immutable `replies` receipt using that actual message as its source; record semantic answers only after checking that the choice is still current and open. An already committed delivery must not execute twice. Preserve historical comments without applying them to a newer choice. If the payload is missing, stale, or conflicts with the prose, do not invent its bindings or claim the reply was saved. Reconcile it with the user when necessary. UI drafts and delivery acknowledgements are not user-answer evidence.

For an old delivered Blocker Resolve or Acknowledge input, preserve the envelope and record that item as stale. This clears delivery bookkeeping without accepting the retired action, resolving the obstacle, or asking the user to resend it.

For a Blocker requiring login or a web action, provide the actual action URL. When the supported browser path allows it, open the page once, verify the page opened, and keep the link available in the card. Never claim a page opened based only on issuing a command. Do not reopen it on every render. The optional `action_url` field is omitted for blockers with no relevant web destination; do not invent a URL. Opening a link or receiving 'I logged in' is not proof that the blocker is resolved: verify the affected connection before changing its status.

Use the bundled [JSON Schema](../../schema/journal.schema.json) for field names. Set `Decision.required: true` only when that answer is necessary to proceed on its linked request; optional preferences do not justify stopping other work. Keep `agent_assumption` separate from `user_answer`. A background checkpoint names its `continuing_run.request_ids`, current `observed_turn_id` and evidence. Each active/waiting request needs its own applicable boundary; do not invent extra blockers to satisfy the validator. Parent completion cannot hide unfinished child scope.

Internal AI-to-AI messages do not generate human turns. A proposal from another agent is not user authorization. Keep execution logs and technical task graphs in their original workspace, linked only when relevant.

Use a web widget or HTML explanation when a diagram or before/after comparison clarifies a decision. Reference the same decision and revision. This is additional communication, not the persistent tracker or proof of an answer.

The first usable version requires a connected deterministic writer and renderer. This instruction file alone does not implement them. If missing, report that limitation instead of claiming Markdown achieves automatic persistent tracking. Preserve user stops during hook or recovery handling. This skill does not authorize new tools or paid inference.
